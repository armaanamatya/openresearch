## Section 4 — Log noise patterns

### N-001 — aclose() noise has two severities
See B-001 above. The root-path stderr noise is cosmetic, but the same SDK
cleanup family is fatal in the `implement_baseline` sub-agent path. Quieting
the root-path noise still matters because it hid the true failure mechanism
during the first pass; fixing the sub-agent path is reproduction-blocking.

### N-002 — `seconds_since_event=N` heuristic is misleading (TWO instances now)
The derived `run_state.substate.seconds_since_event` is unreliable in BOTH directions:

**Instance 1 (false-quiet):** At 21:25, during the actual SDK aclose() hang, `seconds_since_event` reset to 13s repeatedly even though no real progress was happening. The heuristic counts *any* state-tracker write as an "event", masking real stalls.

**Instance 2 (false-stuck):** At 21:39, `implement_baseline` started and is legitimately running (Sonnet sub-agent writing baseline code, which takes 5–15min). The derived state flipped to `kind=stuck` after ~60s and has been emitting `stuck` events every 5s for the past ~2 minutes. This is a **false positive** — the primitive is doing real work, but no intermediate state events are emitted from inside the sub-agent call.

**Combined fix:** the derived state needs three changes:
1. Distinguish `heartbeat-driven state tick` from `real primitive completion` (don't reset `seconds_since_event` on heartbeat-only ticks)
2. Have a per-primitive expected-duration table — `implement_baseline` should have a longer stuck threshold (≥ 600s) than `understand_section` (≥ 60s)
3. When `stuck` is emitted, include a `reason` field (currently always `None`) explaining why the heuristic fired

### N-003 — `implement_baseline` emits no progress events while it runs
The historical funnel showed 7/8 runs never reached `implement_baseline` and 6/7 of those that reached it died there. With zero intermediate events from inside the sub-agent (no token-streaming, no tool-call updates, no heartbeat), it's invisible *whether* it's making progress, retrying, or hung in the SDK. This is what makes the stuck-detection heuristic both important and unreliable.
**Fix surface:** the `implement_baseline` primitive should emit a `sub_agent_token` or `sub_agent_tool_call` event every 30s, even if just a heartbeat-with-context, so the derived state can distinguish "Sonnet thinking" from "Sonnet hung in SDK".

### B-NEW-001 🔴 — `implement_baseline` 240s SDK pre-emit stall
See B-001 (re-elevated). Specifically: the primitive's internal stall-detector returns an error after 240s but the upstream SDK bug is the root cause. **First implement_baseline attempt failed with this at 21:40:09.**

### B-NEW-002 🟠 — `run_experiment` called with error-dict instead of `code_path`
**Live evidence (21:40:09):** when `implement_baseline` failed and returned `{"success": False, "error": "..."}`, the root model passed THAT DICT to `run_experiment(code_path=...)`. The primitive caught the type error cleanly:
```
"run_experiment: code_path must be a non-empty string path, got dict"
```
**Why this matters:** the root model is supposed to check primitive return values for `success/ok` before chaining them, but it didn't. This is a prompt-or-system-prompt bug — the root needs an explicit instruction to inspect `implement_baseline`'s return type before passing to `run_experiment`.
**Fix surface:** either (a) `implement_baseline` raises on failure instead of returning an error dict, or (b) the system prompt explicitly warns the root to check `result["success"]` before chaining.
**This is also the kind of cross-primitive failure that HALO Lane D would catch** if we'd had the LLM-mining version. The funnel-collapse pattern in the stats doc Finding 3 is probably this same bug class repeating across runs.

### B-NEW-003 🟠 — `worker_report_failed` has `error: null` (silently swallowed)
**Live evidence (21:40:09):** when `implement_baseline` failed, the corresponding `worker_report_failed` event has:
```json
{
  "event": "worker_report_failed",
  "agent_id": "implement_baseline",
  "error": null,
  "blockers": []
}
```
The actual error message is in the primitive's `result_summary` dict, NOT in the worker report's `error` field. The worker reporter is supposed to surface failure details for observability — but isn't.
**Impact:** anyone watching dashboard_events for failures will see `error: null` and assume nothing went wrong, when actually the primitive caught an error and returned it as data. Silently swallowed.
**Fix surface:** when `worker_report_failed` fires, extract the error from the primitive's result and populate the report's `error` field.

### B-NEW-004 🔴 — `implement_baseline` retry path can fail after writing code

**Live evidence:** attempt #2 wrote files under `runs/prj_ac41983c934a3432/code`
(`config.json`, `requirements.txt`, `rubric_guard.py`, etc.) and the derived
state flipped from `stuck` to `working`, but the primitive still ended as
`status=error` at `21:45:20`. The worker report underneath says:
`Claude Code returned an error result: success`.

This is worse than the pure pre-emit stall: code exists on disk, but the
primitive still returns `Exception`, so the root never receives the usable
`code_path`. The fallback that harvests on-disk files after SDK cleanup stalls
did not convert this attempt into success.

**Fix surface:** in `implement_baseline`, if `commands.json` or minimally valid
code artifacts exist when the SDK returns a malformed/error result, harvest the
code directory and return the path, or emit a precise typed error explaining why
the files are unusable.

### B-NEW-005 🟠 — final candidate proposal is empty

After rubric=0, `propose_improvements` returned a list with one candidate, but

```json
{"id": "", "description": "", "category": "", "title": "candidate", "reasoning": ""}
```

The UI and final report cannot explain what the agent wanted to try next. This
also makes GEPA/HALO downstream mining weaker because the candidate record has
no semantic content.

**Fix surface:** enforce a non-empty candidate schema in
`propose_improvements`; reject or repair candidates whose `id`, `description`,
or `reasoning` are blank.

### B-NEW-006 🟠 — terminal status axes disagree

`dashboard_events.jsonl` emits `run_complete.status="failed"` and
`demo_status.run_state.kind="failed"`, but `demo_status.status="completed"`.
The code comment in `origin/main:backend/agents/rlm/run.py` treats process
completion and reproduction verdict as separate axes, but the UI/operator sees
this as contradictory.

**Fix surface:** expose both axes explicitly in the status payload, e.g.
`process_status=completed` and `verdict=failed`, rather than overloading a
single visible `status` pill.
