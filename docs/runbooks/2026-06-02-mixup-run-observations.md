## Bugs discovered

### BUG-NEW-046 — `paper_grounding_failed` false positive on dict-type dataset entries

**Observed**: Both `plan_reproduction` and `implement_baseline` emitted `run_warning code=paper_grounding_failed` for CIFAR-10 and ImageNet.

**Root cause**: The root model returned the `datasets` field as a list of dict objects (e.g. `{"name": "CIFAR-10", "source": "torchvision", ...}`). When the grounding validator receives these, the entries arrive as Python dict objects. At the call site in `primitives.py:1346`, `method_spec` is passed directly to `assert_paper_grounded`. The `PaperClaimMap` constructor stringifies dicts into `str(value)` when placing them into the `datasets: list[str]` field, producing the string `"{'name': 'CIFAR-10', 'source': 'torchvision', ...}"`. This exact string is not in the paper text — hence the false positive.

**Impact**: Low — advisory only, the run continues. But the warning is noisy and misleading.

**Fix options**:
1. In `paper_grounding.py::assert_paper_grounded`: before checking `ds` in paper text, detect if `ds` starts with `{` or matches a dict-repr pattern and extract the `name` sub-key for checking.
2. In `PaperClaimMap` constructor: if a dataset entry is a dict, extract `entry["name"]` rather than `str(entry)`.
3. In the root system prompt: explicitly instruct the root that `datasets` must be a flat list of plain name strings (not dict objects).

**Severity**: Low. **Status**: Open.

### BUG-NEW-047 — `compute_scope_invalid` — root returns string for `compute_scope` field

**Observed**: `plan_reproduction` emitted `run_warning code=compute_scope_invalid` — "compute_scope must be a dict or null; got 'str': CPU-only execution per environment_spec; no CUDA available..."

**Root cause**: The `environment_spec.json` generated by `detect_environment` contains `"compatibility_notes": "Generated for pytorch==2.2.0 on CPU."`. The `detect_environment` primitive always runs LOCALLY (on the dev machine, not on RunPod), so this CPU note reflects the local dev environment, not the RunPod pod. The root model read this note and concluded the experiment should be CPU-only, passing a plain string to `compute_scope`.

**Impact**: Low for this run — `train.py` has proper GPU detection (`HAS_GPU = torch.cuda.is_available()`), so it ran the full 100-epoch GPU path regardless. The warning is a metadata/schema mismatch, not a runtime failure.

**Fix**: Add to the root system prompt (or to `detect_environment` output): a note that `compatibility_notes` reflects the LOCAL developer machine environment used to generate the spec, NOT the RunPod sandbox where experiments execute. The RunPod image always has CUDA available.

**Severity**: Low. **Status**: Open.

### BUG-NEW-048 — GEPA `plan_reproduction` phase produces 0 candidates; timeout consumed by seed evaluation

**Observed**: 
- `gepa_phase_start` at 04:46:02
- `gepa_phase_complete` at 04:48:11 (elapsed: 129s)
- Zero `gepa_candidate_proposed` / `gepa_candidate_accepted` / `gepa_candidate_rejected` events
- `gepa_examples.jsonl` not updated (previous run's 4 entries remain unchanged)

**Root cause**: `PlanReproductionEvaluator` scores the seed prompt by calling `ctx.llm_client.complete` (claude-oauth path). This LLM call takes ~2 minutes (claude-oauth subscription has higher latency than API). The configured timeout for `plan_reproduction` GEPA is 60s (`gepa_timeout_plan_s`). By the time seed scoring completes at ~129s, the timeout is already exceeded, so `run_gepa_mini` exits with 0 proposals — returning the seed prompt unchanged.

The fail-soft mechanism correctly engaged (`best_prompt = seed`, run not blocked). But the 2-minute delay provides no optimization benefit and consumes wall-clock.

**Impact**: Medium — GEPA provides zero optimization for all runs that use the claude-oauth reflection model with the current 60s timeout. Every plan_reproduction call loses ~2 minutes to seed evaluation with no benefit.

**Fix options**:
1. Increase `gepa_timeout_plan_s` from 60s to 240s in `backend/config.py` — allows seed evaluation + at least 1-2 proposals.
2. Make seed evaluation optional / async — start generating proposals before seed is scored, using 0.0 as the baseline score.
3. Add a fast heuristic pre-check: if the reflection model responds in >30s for seed scoring, skip the timeout and return immediately instead of waiting.
4. Cache the seed score across runs so it doesn't need re-evaluation on every run.

**Code locations**:
- `backend/agents/gepa/hooks.py::gepa_pre_call` — calls `run_gepa_mini` with timeout
- `backend/agents/gepa/adapters/plan_reproduction.py` — `PlanReproductionEvaluator`
- `backend/config.py` — `gepa_timeout_plan_s` (currently 60s)

**Severity**: Medium (GEPA effectively disabled on claude-oauth path). **Status**: Open.

### BUG-NEW-049 — TRANSIENT_500 escalates GPU tier same as CAPACITY_EXHAUSTED

**Observed**: RTX 4090 received 3 × `RUNPOD_TRANSIENT_500` (HTTP 500 from RunPod API, not a pool-empty signal), which triggered the same 3-retry-then-escalate path as `RUNPOD_CAPACITY_EXHAUSTED`.

**Root cause**: The retry/escalation handler treats any sandbox failure as a candidate for GPU escalation after 3 retries, regardless of error class. `TRANSIENT_500` (momentary API hiccup) and `CAPACITY_EXHAUSTED` (GPU pool empty) both hit the same escalation path.

**Impact**: Medium — uses up escalation slots unnecessarily when the target GPU tier is available but the RunPod API was momentarily flaky. Results in running on a more expensive GPU (A6000 $0.49/hr vs RTX 4090 $0.34/hr).

**Fix**: In the escalation handler, distinguish error classes:
- `RUNPOD_TRANSIENT_500` → increase backoff and retry same tier (e.g. 5× longer delay) before consuming an escalation slot.
- `RUNPOD_CAPACITY_EXHAUSTED` → escalate immediately.

**Code location**: `backend/services/runtime/` (sandbox retry/escalation logic).

**Severity**: Low-Medium. **Status**: Open.

### BUG-NEW-050 — Root model passes empty `results={}` to `verify_against_rubric` (HIGH — caused false `verdict=failed`)

**Observed**: `verify_against_rubric` was called with `results={}` (empty dict). All rubric leaves scored 0.0 with `justification: "degraded_no_metrics"`. Final report shows `verdict=failed`, `overall_score=0.0` despite successful training.

**Root cause confirmed via `primitive_cache.jsonl`**: the cached payload for `verify_against_rubric` shows `results.success=None` and `results.metrics={}`. The root model constructed an empty results dict instead of passing the `run_experiment` output.

**Code path**: When `results={}`:
- `verify_against_rubric` computes `has_experiment_result = False` → `degraded = False`
- `score_reproduction` is called with `degraded=False`, runs the LLM grader
- But the LLM grader sees no metrics in the evidence (the `code/metrics.json` path used for evidence hashing doesn't exist at `code/metrics.json` — it lives at `code/outputs/{run_id}/metrics.json`)
- The grader scores 0.0 on every leaf because there's no metric evidence in `code/` root
- Actually: `degraded=False` but `graded=0` → honesty guard fires if leaf_count > 0 → returns error OR the grader correctly returns 0 when it cannot find metric evidence

Wait, further investigation is needed here. The `degraded_no_metrics` justification ONLY appears in the `if degraded:` branch. But `degraded=False` was passed. This suggests either:
1. The LLM grader produced 0 graded leaves AND `degraded` was re-evaluated True somewhere
2. A cached degraded result was returned (cache key: `results={}` + rubric hash matches a previous run)

**Most likely mechanism**: The `primitive_cache` for `verify_against_rubric` returned a CACHED result from a previous run (Run #1 or Run #2) where `results={}` was also passed and the cached response had `degraded_no_metrics`. Cache key collision on empty results dict.

**Impact**: HIGH — training was successful (Mixup 94.5% > ERM 93.4%, qualitative_pass=True) but the run reported `verdict=failed` due to this bug. Forced another `run_experiment` attempt which also failed (A6000 capacity exhausted).

**Fix options**:
1. **Root prompt**: Explicitly instruct the root to pass the full `run_experiment` return value to `verify_against_rubric`, not a reconstructed or empty dict.
2. **Code-level validation**: In `verify_against_rubric`, if `results={}` (empty), look up the most recent successful entry in `experiment_runs.jsonl` and use those metrics.
3. **Cache invalidation**: Don't cache `verify_against_rubric` results when `results` is empty — these are meaningless and should not be cached.

**Severity**: HIGH (causes false `verdict=failed` despite successful training). **Status**: Open (BUG-NEW-050).
